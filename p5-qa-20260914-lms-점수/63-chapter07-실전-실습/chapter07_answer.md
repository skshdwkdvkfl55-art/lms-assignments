# 2. 프로젝트 범위와 요구사항 읽기

## 2-1. 포함 범위

본문을 그대로 복사하지 말고 자신의 말로 정리합니다.

```text
1. 수강생(students), 강사(instructors), 강좌(courses)의 기본 식별 정보 및 연락처/이메일 고유성 관리
2. 강좌 등록 시 필수 담당 강사 지정(1:N) 및 음수 방지 가격(price >= 0) 비즈니스 룰 적용
3. 수강생과 강좌 간의 M:N 관계를 해소하는 수강신청 사건(enrollments) 관리 및 4대 상태값(신청, 수강중, 완료, 취소) 추적
4. 수강신청 시점의 결제 금액 스냅샷(recorded_amount) 보존 및 조건부 부분 고유 인덱스를 통한 유효 상태 중복 신청 차단
```

## 2-2. 제외 범위

```text
1. 실제 전자결제(PG) 연동, 카드 승인 번호, 계좌이체 등 외부 결제 게이트웨이 트랜잭션
2. 동영상 스트리밍 서비스 연동, 일시정지, 배속, 강의 구간별 초 단위 진도율 추적
3. 강좌별 최대 수강 정원(Capacity) 초과 방지 락(Locking) 및 실시간 대기 번호 부여 시스템
4. 강사 수당/급여 자동 정산, 세무 회계 전표 발행 및 프로모션 할인 쿠폰 발급/사용 이력 추적
```

### 범위를 명확하게 정해야 하는 이유

```text
1. MVP(최소 기능 제품) 단계에서 핵심 비즈니스 무결성 규칙(중복 수강 방지, 참조 무결성, 금액 일관성)에 온전히 집중하기 위함.
2. 현실 세계의 모든 요구사항을 한 번에 담으려다 스키마가 과도하게 복잡해져 프로젝트 일정과 품질이 무너지는 것을 방지하기 위함.
3. 개발팀, 비즈니스 기획자, 데이터베이스 관리자가 '이번 단계에서 데이터베이스가 반드시 보장해야 할 책임 한계선'을 명확히 합의하기 위함.
```

## 2-3. 요구사항 / 프로젝트 결정 / 미확정 질문 구분

아래 항목 중 대표 항목을 정리합니다.

| ID | 종류 | 내용 요약 | DB 구조/규칙에 미치는 영향 |
| --- | --- | --- | --- |
| P07-R01 | 요구사항 | 수강생 정보와 이메일 고유성 보장 | students 테이블 생성, email 열에 `uq_course_students_email` UNIQUE 제약 적용 |
| P07-R05 | 요구사항 | 수강신청 4대 상태값 관리 | enrollments.status 열에 `chk_course_enrollments_status` CHECK('신청','수강중','완료','취소') 적용 |
| P07-R07 | 요구사항 | 데이터 변경에도 불변하는 식별자 유지 | 자연키(이메일 등) 대신 `INTEGER GENERATED BY DEFAULT AS IDENTITY` 대리키 PK 채택 |
| P07-D02 | 프로젝트 결정 | 결제 당시 금액 스냅샷 분리 보존 | enrollments에 `recorded_amount NUMERIC(12,0)`를 두어 courses.price와 분리 보존 |
| P07-D03 | 프로젝트 결정 | 유효 수강권 중복 차단 및 취소 후 재신청 허용 | `CREATE UNIQUE INDEX ... WHERE status IN ('신청', '수강중')` 부분 고유 인덱스 적용 |
| P07-Q01 | 미확정 질문 | 무료 이벤트 강의(0원) 및 무료 신청 허용 여부 | CHECK(price >= 0), CHECK(recorded_amount >= 0)으로 0원을 허용하도록 유연하게 설계 |

### 미확정 질문을 바로 제약조건으로 만들면 안 되는 이유

```text
1. 비즈니스 정책이 미확정된 상태에서 과도하게 엄격한 제약조건(예: price > 0 강제)을 걸면, 추후 '0원 무료 특강 이벤트'를 진행할 때 시스템 전체가 마비되는 심각한 장애가 발생함.
2. 운영 중인 데이터베이스에서 제약조건을 수정하거나 삭제하는 마이그레이션 작업은 테이블 락(Lock)을 유발하고 데이터 마이그레이션 비용이 매우 큼.
3. 비즈니스 결정이 완료되기 전까지는 시스템 확장을 가로막지 않도록 유연한 경계선(price >= 0)을 유지하되, 애플리케이션 레벨에서 정책을 제어하는 것이 안전함.
```

# 3. 네 테이블의 한 행 의미와 관계

## 3-1. 한 행 의미

```text
course_project.students 한 행 = 시스템에 회원으로 가입한 유일한 수강생 1명의 식별자 및 기본 계정 정보
course_project.instructors 한 행 = 강좌를 개설하고 강의를 진행하는 전문 강사 1명의 프로필 정보
course_project.courses 한 행 = 특정 강사가 개설하여 운영하는 독립된 온라인 강의 강좌 1개
course_project.enrollments 한 행 = 특정 수강생이 특정 강좌에 대해 특정 일자에 발생시킨 '수강신청 사건(Event)' 1건의 트랜잭션 기록
```

## 3-2. 키와 중요 규칙

| 테이블 | PK | FK | 중요 규칙 |
| --- | --- | --- | --- |
| students | `id` (IDENTITY) | 없음 | `email` UNIQUE, `name`/`email` 공백 금지 CHECK |
| instructors | `id` (IDENTITY) | 없음 | `email` UNIQUE, `name`/`email`/`specialty` 공백 금지 CHECK |
| courses | `id` (IDENTITY) | `instructor_id` -> instructors(id) | ON DELETE RESTRICT, `price >= 0`, `level` IN ('basic','intermediate','advanced') |
| enrollments | `id` (IDENTITY) | `student_id`, `course_id` | ON DELETE RESTRICT, `status` 4종 제약, `recorded_amount >= 0`, 활성 부분 인덱스 |

## 3-3. 관계를 양방향 문장으로 작성

```text
instructors ↔ courses:
- 한 명의 강사는 0개 이상의 강의를 개설할 수 있다. (1:N)
- 하나의 강의는 반드시 정확히 한 명의 담당 강사를 가져야 한다. (N:1, ON DELETE RESTRICT)

students ↔ enrollments:
- 한 명의 학생은 0건 이상의 수강신청을 할 수 있다. (1:N)
- 하나의 수강신청은 반드시 특정 학생 1명에 의해 이루어져야 한다. (N:1, ON DELETE RESTRICT)

courses ↔ enrollments:
- 하나의 강의는 0명 이상의 학생에 의해 수강신청될 수 있다. (1:N)
- 하나의 수강신청은 반드시 특정 강의 1건을 대상으로 해야 한다. (N:1, ON DELETE RESTRICT)
```

### 학생과 강의의 N:M 관계가 `enrollments`를 통해 어떻게 바뀌는지 설명

```text
학생 1명은 여러 개의 강의를 들을 수 있고, 강의 1개도 여러 명의 학생이 들을 수 있는 다대다(N:M) 관계입니다.
관계형 데이터베이스에서는 테이블 간에 다대다 관계를 직접 외래키로 연결할 수 없습니다. (배열로 저장하거나 중복 행을 만들어 제1정규형을 위반하게 됨)
따라서 중간에 `enrollments`라는 연결/사건 테이블을 배치하여:
1. students(1) ───< enrollments(N)
2. courses(1)  ───< enrollments(N)
이라는 2개의 안전하고 정규화된 1:N 관계로 전환하여 완벽한 참조 무결성을 보장합니다.
```

### `enrollments`가 단순 연결 테이블이 아니라 사건 테이블이라고 볼 수 있는 이유

```text
단순 연결 테이블(Cross Table)은 두 부모의 PK(`student_id`, `course_id`)만을 묶어 관계 유무만을 표현합니다.
반면 `enrollments`는:
1. 사건이 발생한 시점 (`enrolled_at`)
2. 사건의 현재 진행 상태 (`status`: 신청, 수강중, 완료, 취소)
3. 사건 발생 당시의 거래 조건 스냅샷 (`recorded_amount`: 결제 시점 금액)
이라는 독립적인 비즈니스 생애주기 속성들을 풍부하게 가지고 있으므로, 현실의 업무 트랜잭션을 기록하는 명확한 '사건 테이블(Event Entity)'입니다.
```

# 4. `recorded_amount`의 의미 이해

```text
courses.price = 특정 강의의 현재 시점 공식 판매 가격 (물가 상승, 할인 정책에 따라 미래에 언제든 변동될 수 있는 가변값)
enrollments.recorded_amount = 학생이 수강을 신청한 바로 그 순간에 합의되고 기록된 실제 결제 금액의 불변 스냅샷(Snapshot)
```

### 두 값이 처음에는 같아도 같은 의미가 아닌 이유

```text
강의를 개설할 때 등록한 가격(price=100,000원)과 학생이 신청할 당시의 금액(recorded_amount=100,000원)은 처음에는 수치가 우연히 같을 수 있습니다.
그러나 시간이 흘러 학원 정책상 해당 강의 가격이 150,000원으로 인상되었을 때, 만약 `recorded_amount`를 따로 저장하지 않고 `courses.price`를 참조하여 과거 매출을 계산하면 과거에 100,000원을 낸 학생의 결제액까지 150,000원으로 둔갑하는 심각한 회계 왜곡이 발생합니다.
따라서 두 값은 '현재 가격'과 '과거 결제 이력 스냅샷'이라는 완전히 서로 다른 비즈니스 의미를 갖습니다.
```

### `recorded_amount`를 실제 결제 성공액이나 회계 매출로 해석하면 안 되는 이유

```text
1. 수강신청 상태가 '신청'인 경우, 장바구니에 담아 신청서만 제출하고 아직 카드 결제가 완료되지 않은 미수금 상태일 수 있습니다.
2. 수강신청 상태가 '취소'로 전이된 경우, 결제 대금이 전액 환불되어 실제 기업의 통장에 남은 순매출은 0원이 되어야 합니다.
3. 실제 회계 매출을 확정하기 위해서는 결제 시스템(PG)의 거래 승인 번호, 환불 일자, 카드 수수료 정산 내역과의 대사(Reconciliation) 과정이 반드시 수반되어야 합니다.
```

# 12. 개인 프로젝트 ERD와 한 행 의미

## 12-1. 테이블 후보

```text
1. library_project.members (회원 테이블, 1명 정보)
2. library_project.books (도서 서지 정보, 1종 책 정보)
3. library_project.book_copies (실물 장서 권 정보, 바코드 부착된 실물 1권)
4. library_project.loans (도서 대여 사건 이력, 대출 행위 1건)
```

## 12-2. 관계 문장

```text
- books(1) ↔ book_copies(N): 한 종의 도서 서지 정보는 도서관에 여러 권의 실물 장서(복본)로 존재할 수 있다.
- members(1) ↔ loans(N): 한 명의 회원은 도서관 이용 기간 동안 여러 번 도서를 대여할 수 있다.
- book_copies(1) ↔ loans(N): 실물 1권의 책은 여러 회원에게 거쳐가며 여러 번 대여될 수 있다.
```

## 12-3. ERD

```
[ 회원: members ] ──────(1:N)──────< [ 대여: loans ] >──────(N:1)────── [ 실물도서: book_copies ] ──────(N:1)────── [ 도서서지: books ]
  - id (PK)                            - id (PK)                           - id (PK)                               - id (PK)
  - name (NOT NULL)                    - member_id (FK)                    - book_id (FK)                          - isbn (UQ)
  - email (UQ)                         - copy_id (FK)                      - barcode (UQ)                          - title
  - phone (UQ)                         - loan_date                         - status (대출가능/대출중/...)          - author
                                       - due_date                          - shelf_location                        - publisher
                                       - return_date
                                       - status (대출중/반납완료/연체/분실)
                                       - recorded_fee (연체료/변상금 스냅샷)
```

### Chapter 05~06 ERD에서 이번에 바꾼 점

```text
1. 책 테이블을 '서지 정보(books)'와 '실물 도서(book_copies)'로 명확히 정규화 분리하여 복본(같은 책 여러 권) 관리 지원.
2. loans 테이블에 Chapter 07의 핵심 기법인 '부분 고유 인덱스'를 도입하여 활성 대출만 중복을 방지하고 반납 이력을 보존하도록 구조 개선.
3. 분실 변상금 및 연체료 스냅샷 컬럼(`recorded_fee`)을 추가하여 회계 데이터의 불변성을 확보.
```

# 14. AI를 프로젝트 리뷰어로 사용

## 14-1. AI에게 전달한 핵심 자료

```text
1. 도서관 대여 시스템 4개 테이블 스키마 DDL (members, books, book_copies, loans)

```

## 14-2. 내가 사용한 프롬프트

```text
"나는 데이터베이스 입문 과정에서 도서관 대출 관리 시스템을 설계하고 있어.
현재 4개 테이블 구조와 부분 고유 인덱스를 작성했는데,
1. 실무 비즈니스 관점에서 발생할 수 있는 데이터 무결성 결함이 있는지,
2. 과도한 복잡성으로 인해 초보자가 다루기 힘든 불필요한 제약이 있는지,
비판적인 관점에서 리뷰해 주고 제안 사항을 알려줘."
```

## 14-3. AI 제안 검토

| AI 제안 내용 | 판정 (수용/수정/보류/거절) | 판단 이유 |
| --- | --- | --- |
| 회원 탈퇴 시 기존 대여 이력을 CASCADE로 일괄 삭제 제안 | **거절** | 회원이 탈퇴하더라도 과거 대출 통계 및 분실 변상금 회계 장부가 보존되어야 하므로 RESTRICT 유지. |
| 반납일이 대여일보다 앞서는 것을 막는 CHECK (return_date >= loan_date) 제약 추가 | **수용** | 날짜 역전 현상은 명백한 논리 오류이므로 테이블 레벨에서 강제하는 것이 매우 적절함. |
| RFID 실시간 도서 위치 추적 테이블 추가 제안 | **보류** | MVP 설계 범위를 넘어서는 고도화 기능이므로 2차 프로젝트로 보류. |
| 연체료 계산을 위한 트리거(Trigger) 자동 생성 제안 | **수정** | 트리거는 아직 학습 전 단계이므로, 배치 쿼리 또는 애플리케이션 계산 후 UPDATE하는 방식으로 수정 반영. |

### AI가 미확정 정책을 임의로 확정하려 한 부분이 있었나요?

```text
네, AI가 연체료 부과 방식을 '일 500원 자동 과금'으로 기정사실화하여 컬럼과 연산식을 생성하려 했습니다.
아직 도서관 내부 규정상 '연체 일수만큼 대출 정지' 페널티를 줄지 '금전 연체료'를 부과할지 미확정(P07-MQ01) 상태이므로, 임의 확정을 거절하고 유연한 비고 컬럼으로 남겨두었습니다.
```

### AI가 제안한 규칙 중 아직 배우지 않은 기능이라 보류한 것이 있나요?

```text
대출 기한 초과 시 매일 자정에 자동으로 status를 '연체'로 바꾸는 PostgreSQL pg_cron 스케줄러와 PL/pgSQL 트리거 생성을 제안받았으나, 현재 학습 범위를 벗어나므로 보류하고 수동 SQL 배치 방식으로 처리하도록 조정했습니다.
```

```text
2. 서지 정보와 실물 도서 복본(Copy) 분리 구조의 유효성을 객관적으로 교차 검증받을 수 있었습니다.
```

# 15. 최종 성찰

```text
1. 부분 고유 인덱스(Partial Unique Index)의 실무적 가치:
   단순 UNIQUE 제약은 과거 취소/반납 이력까지 차단해 버리는 치명적 한계가 있었으나, WHERE 조건을 부여한 부분 인덱스를 통해 '현재 유효한 대출만 중복 차단'하면서 이력 데이터를 온전히 보존할 수 있는 강력한 무결성 도구를 배웠습니다.

2. 스냅샷 컬럼(recorded_amount)의 중요성:
   데이터베이스는 현재 상태만을 보는 것이 아니라 과거의 거래 내역을 신뢰할 수 있게 보존해야 합니다. 가격 변동과 거래 당시 금액을 분리하는 모델링이 회계 정합성의 기본임을 깨달았습니다.

3. 실패 테스트(Failure Test)의 교훈:
   에러가 발생하는 것은 실패가 아니라, DBMS의 방어벽이 잘못된 데이터의 침입을 성공적으로 차단했다는 가장 확실한 증거라는 점을 배웠습니다.
```
